# Task-Specific Supplementary State for GLMs

## The basic idea

Graph Language Models currently get their graph information through the graph representation itself: the GNN processes (G), produces graph embeddings, and the language model reasons from those embeddings.

GraphModi showed that when the underlying graph changes, it can be useful to actually update the graph and re-encode it rather than just telling the language model about the change in text.

A natural next step is to ask:

**What if we give the GLM additional information about the graph that is useful for a particular task?**

For example, suppose the task is shortest-path reasoning. Instead of expecting the GNN/LLM combination to reconstruct all pairwise distances internally, we could also provide a representation of the pairwise distances in the graph.

The important part is that this extra information should not necessarily be static. If the graph changes, the supplementary information can change too.

---

## Example: Pairwise distances

Suppose the graph is a metro system:

```text
A --- B --- C
      |
      D --- E
```

The graph embedding captures the structure of the metro system.

But for shortest-path questions, we could also provide information such as:

```text
distance(A, B) = 1
distance(A, C) = 2
distance(A, D) = 2
distance(A, E) = 3
distance(C, E) = 4
```

Now imagine the user says:

> "The connection between B and C is closed."

GraphModi would update the graph.

The same idea could apply to the distance information:

```text
Before:

A → C = 2
A → E = 3

After removing B-C:

A → C = ...
A → E = ...
```

The model is therefore not just receiving a changed graph. It is receiving a changed **derived view of the graph** that is particularly useful for the task.

---

## Example: Reachability

Consider:

```text
A --- B --- C

D --- E
```

For a connectivity task, we could provide information about which nodes can reach each other.

Initially:

```text
A ↔ B
A ↔ C
B ↔ C

D ↔ E
```

If the user says:

> "Remove the connection between A and B."

the graph changes, but so does the connectivity information.

The new state becomes:

```text
A

B --- C

D --- E
```

The supplementary information now tells the model that A is no longer connected to B or C.

This is useful because connectivity is a global property that may not be trivial for the model to infer directly from a learned graph representation.

---

## Example: Centrality

Suppose the graph represents a road network:

```text
       B
       |
A --- C --- D --- E
       |
       F
```

C is highly central.

We could provide node-level information such as:

```text
C: high centrality
B: low centrality
A: low centrality
...
```

Now suppose the user says:

> "The road between C and D is permanently closed."

The graph changes, and the centrality values may change as well.

The model could therefore receive an updated representation of which nodes are important in the new graph.

This could be useful for questions such as:

> "Which station is most strategically important?"

or:

> "Which station should we avoid disrupting?"

---

## Example: Community structure

Suppose the graph contains two clusters:

```text
A --- B --- C
|     |
D --- E


F --- G --- H
      |
      I
```

A graph-community algorithm might identify:

```text
Community 1 = {A, B, C, D, E}
Community 2 = {F, G, H, I}
```

The supplementary state could expose this information to the GLM.

Now suppose an edge is added:

```text
E --- G
```

The graph may now have a much stronger connection between the two communities.

The supplementary state could change accordingly.

Questions such as:

> "Which group does station G belong to?"

or

> "Are these two regions becoming more connected?"

could benefit from this additional information.

---

## Example: Ranking

The supplementary state could also be something as simple as a ranking.

Imagine a social network:

```text
A connects to 20 people
B connects to 15 people
C connects to 4 people
D connects to 2 people
```

We could provide:

```text
1. A
2. B
3. C
4. D
```

Then a graph edit occurs:

> "A is no longer connected to B, C, D, ..."

The ranking may change.

Instead of expecting the GLM to calculate the ranking from scratch, the updated ranking can become part of its graph state.

This could apply to:

* degree ranking
* PageRank
* influence
* importance
* popularity
* accessibility

---

## Example: Multiple task-specific views

The interesting part is that different tasks could use completely different supplementary information.

For a metro graph:

**Shortest-path questions**

```text
Graph + pairwise distances
```

**Connectivity questions**

```text
Graph + reachability / components
```

**"Most important station" questions**

```text
Graph + centrality
```

**Community questions**

```text
Graph + community assignments
```

The underlying graph stays the same.

What changes is the additional information supplied alongside the graph.

---

## Why the editability matters

Simply giving a GLM extra features is not particularly novel by itself.

The more interesting idea is that the extra information can be **maintained as the world changes**.

Imagine:

```text
Graph
  +
Shortest-path information
```

Then:

> "Station B is closed."

becomes:

```text
old graph
    ↓
edit
    ↓
new graph

old distances
    ↓
same edit
    ↓
new distances
```

So the system maintains not only a representation of the world, but also useful **derived knowledge about the current world**.

This is especially interesting when the derived information is expensive or difficult to infer from the graph embedding alone.

---

## Example: A recommendation task

Imagine a graph representing a delivery network.

The model has:

```text
G = road network

Supplementary state:
- shortest distance between warehouses and customers
- estimated travel time
- most accessible warehouse
```

A user says:

> "Road A-B is closed."

The system updates the graph.

The relevant supplementary information changes too:

```text
Customer X:
old nearest warehouse = W1
new nearest warehouse = W2

Customer Y:
old travel time = 12 min
new travel time = 19 min
```

The next question:

> "Which warehouse should deliver to X?"

can be answered using the updated state.

---

## Example: Planning

Suppose the graph represents a set of possible actions or transitions.

The supplementary state could contain:

```text
- distance to goal
- reachable states
- cost of each route
- best known route
```

Then an edit changes the world:

> "This action is no longer available."

The graph changes, and the planning-related information changes with it.

The GLM can now reason using both:

```text
what the world looks like
+
what has already been computed about that world
```

---

## The broader intuition

The idea is not necessarily to find one perfect extra feature for GLMs.

It is to explore whether a graph representation can be accompanied by **useful computational views of that graph**, and whether those views can be kept synchronized when the graph changes.

For example:

```text
                 Graph
                   |
       ┌───────────┼───────────┐
       ↓           ↓           ↓
 distances   connectivity   centrality
       ↓           ↓           ↓
     task-specific supplementary state
                   |
                   ↓
                  GLM
```

Different tasks could therefore give the GLM different ways of looking at the same underlying graph.

GraphModi provides a natural starting point because it already gives us the mechanism for changing the underlying graph. The extension is to ask whether **derived task-specific information can participate in the same evolving state**.

---

## Some particularly interesting examples to try

A first set of experiments could use:

* **Pairwise shortest-path distances** — probably the cleanest example.
* **Reachability / connected components** — easy to verify exactly.
* **Node centrality** — tests useful global node-level information.
* **Community assignments** — tests higher-level structural information.
* **Top-(k) rankings** — tests whether explicitly supplied rankings help reasoning.
* **Shortest-path trees** — gives the model a more structured task-specific view than just distances.
* **Number of reachable nodes** — a simple global statistic.
* **Distance-to-target for every node** — especially natural for navigation/planning.

The most compelling initial demonstration would probably be shortest paths: **the graph changes, the distance state becomes stale, and maintaining that state gives the GLM information that is directly relevant to the question being asked.**

---

## A potentially bigger idea

If this works across several different kinds of supplementary information, the eventual idea becomes broader than GraphModi.

Instead of thinking of a GLM as:

```text
Graph → embeddings → LLM
```

we could think of it as:

```text
              ┌── Graph representation
              │
World state ──┼── Task-specific derived state
              │
              └── Other useful computational views
                         ↓
                        GLM
```

The interesting question then becomes whether **GLMs can benefit from maintaining multiple synchronized representations of the same evolving world**, rather than relying on one learned graph representation to capture everything needed for every task.
